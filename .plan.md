# Plan: Fix DSL Debugging + Parallelise Data Processing

## Problem Diagnosis

### 1. Debugging is broken

Script:
```dsl
acb_only: ASSERT COUNT(payroll_fy2024.EMP_ID) WHERE payroll_fy2024.EMP_ID NOT IN employee_master.EMP_ID > 0
```

Parsed as:
- `Statement.label` = `"acb_only"` ← correct
- `Expr::Assert.label` = `None` ← parser only reads quoted string labels inside ASSERT
- `Expr::Assert.lhs` = `Compare { op: Gt, lhs: Aggregate(COUNT ... WHERE ...), rhs: 0 }`
- `Expr::Assert.rhs` = `Bool(true)` ← implicit because no comparison operator after lhs
- `Expr::Assert.op` = `Eq` ← implicit

Evaluated as `(COUNT(...) > 0) = true`:
- `lhs_value`: `"false"`  ← boolean result of inner comparison
- `rhs_value`: `"true"`  ← the implicit rhs
- `passed`: `false`
- `label`: `null`  ← AssertResult takes Expr::Assert.label, ignores Statement.label

**Result**: user sees `false = true` with no label and no idea what the actual count was.

### 2. Performance is single-threaded

`eval_aggregate`, `eval_row_assert`, and `eval_sample` all iterate rows sequentially:
- `all_rows.iter().filter(...)` — serial filter
- `rows.iter().map(|row| self.eval(expr, row))` — serial expression evaluation per row
- `eval_row_assert` checks every row in a single loop

For 100k+ rows this is the bottleneck.

## Phase 1 — Fix Debugging (Immediate Value)

### 1a. Propagate statement labels

In `src/dsl/eval/mod.rs` (`run_script`), when producing `StatementResult::Assert`, merge `stmt.label` into the result if `Expr::Assert.label` is `None`.

**Change**: Add a helper or modify `run_script` to pass the statement label into `eval_assert` and use it as fallback.

### 1b. Show meaningful values for nested comparisons

In `src/dsl/eval/assert.rs` (`eval_assert`), add a heuristic for the common pattern `ASSERT <comparison> = true` (which is how `ASSERT a > b` parses when the user omits `= true`):

When `op == Eq`, `rhs` evaluates to `Bool(true)`, and `lhs` is `Expr::Compare`:
- Evaluate the inner `lhs` and `rhs` of the comparison
- Report those values instead of the boolean result
- Use the inner comparison operator in `AssertResult.op`

Example output after fix:
```json
{
  "kind": "assert",
  "label": "acb_only",
  "lhs_value": "0",
  "rhs_value": "0",
  "op": ">",
  "passed": false
}
```

### 1c. (Optional but high value) Add row-level assert detail

For row-level assertions (`eval_row_assert`), the current `lhs_value` is `"N/M rows pass"`. This is useful but could be enhanced. Keep as-is for now — the label + aggregate fixes solve the immediate pain.

## Phase 2 — Parallelise Row Processing (Performance)

### 2a. Add `rayon` dependency (native only)

Add to `Cargo.toml` under `[target.'cfg(not(target_arch = "wasm32"))'.dependencies]`:
```toml
rayon = "1"
```

WASM compatibility is preserved because the dependency is gated.

### 2b. Make `EvalDataSource` thread-safe

In `src/dsl/datasource.rs`, add `Send + Sync` bounds:
```rust
pub trait EvalDataSource: Send + Sync {
    fn rows(&self, table: &str) -> Result<&[Row], EvalError>;
}
```

`InMemoryDataSource` (backed by `HashMap<String, Vec<Row>>`) automatically satisfies these bounds.

### 2c. Parallelise `eval_aggregate` (`src/dsl/eval/aggregate.rs`)

Replace serial filtering + mapping with `rayon::par_iter`:

```rust
use rayon::prelude::*;

let rows: Vec<&Row> = all_rows
    .par_iter()
    .filter(|row| {
        filter.as_ref().map(|f| {
            self.eval(f, row)
                .map(|v| v.as_bool().unwrap_or(false))
                .unwrap_or(false)
        }).unwrap_or(true)
    })
    .collect();

let values: Vec<Value> = rows
    .par_iter()
    .map(|row| self.eval(expr, row))
    .collect::<EvalResult<Vec<_>>>()?;
```

Keep DISTINCT deduplication and final aggregation serial (DISTINCT is hard to parallelise efficiently and is rarely used).

### 2d. Parallelise `eval_row_assert` (`src/dsl/eval/assert.rs`)

Pre-check the first row to catch `UnknownColumn` errors before parallelising:

```rust
if let Some(first) = rows.first() {
    if let Err(EvalError::UnknownColumn(col)) = self.eval(lhs, first) {
        return Err(EvalError::UnknownColumn(col));
    }
}
```

Then count passes in parallel:

```rust
let pass_count = rows.par_iter()
    .filter(|row| {
        if is_bool_assert {
            self.eval(lhs, row)
                .map(|v| v.as_bool().unwrap_or(false))
                .unwrap_or(false)
        } else {
            self.eval(lhs, row)
                .map(|lv| self.apply_cmp(op, &lv, &rv))
                .unwrap_or(false)
        }
    })
    .count();
```

### 2e. Parallelise sample filtering (`src/dsl/eval/sample.rs`)

Replace the serial `filter` with `par_iter().filter().collect()`:

```rust
let filtered: Vec<&Row> = all_rows
    .par_iter()
    .filter(|row| {
        filter.as_ref().map(|f| {
            self.eval(f, row)
                .map(|v| v.as_bool().unwrap_or(false))
                .unwrap_or(false)
        }).unwrap_or(true)
    })
    .collect();
```

Sampling algorithms (MUS, random, systematic, stratified) operate on the filtered result set and are inherently serial — keep them as-is.

### 2f. Verify no regressions

- All existing DSL tests in `src/dsl/tests/` must pass
- WASM build (`vinrouge-web`) must still compile (rayon is excluded, `Send + Sync` bounds are harmless on WASM)
- Desktop build (`vinrouge-desktop`) must compile and link `rayon`

## Expected Outcome

1. **Debugging**: Assertions show the statement label and actual numeric values (e.g. `0 > 0` instead of `false = true`).
2. **Performance**: On multi-core machines, aggregate queries and row-level assertions on large datasets should see near-linear speedup with thread count for the filtering/evaluation phases.
